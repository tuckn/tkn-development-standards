# CHANGELOG規約

Gitで管理するリポジトリに置く `CHANGELOG.md` について、置く条件、作るとき、書くこと、書き方を定めます。

## 1. 位置付けと適用範囲

- 本書は、Gitで管理するすべてのリポジトリに適用します。CLIなどのコードのリポジトリに限らず、スライドや動画の制作フォルダ、文書やノートのリポジトリも含みます。remoteの有無や、公開するかどうかは問いません。
- リポジトリをGitで管理するのは、変更の履歴を残すつもりがあるからです。Gitの履歴には、commitごとの差分が残ります。ただ、何が・なぜ変わり、読み手にどんな影響があるかは、まとめて読めません。それを読めるようにするのが `CHANGELOG.md` です。
- READMEとの分担は [CLIリポジトリREADME執筆規約](readme-writing.md) の3.1に従います。Python CLIでは、[Python CLI開発基本方針](python-cli-development.md) の11.7も合わせて守ります。
- 対象リポジトリの指示に別の決まりがあれば、そちらを優先し、理由をREADMEかCHANGELOGに残します。

## 2. 置く場所と作るとき

- リポジトリの直下に `CHANGELOG.md` を置き、READMEからリンクします。
- 新しいリポジトリでは、Gitで管理し始めるときに作ります。最初の項目には、始めたときの中身（主な機能、成果物、元にしたもの）を書きます。
- まだないリポジトリでは、確かめられるGitの履歴とREADMEなどの記録から、主な変更をまとめて作ります。根拠のない日付や変更は補わず、確かめられた範囲を書きます。
- READMEなどに変更の経緯が書いてあれば、CHANGELOGへ移し、READMEには今の状態の説明だけを残します。

## 3. 書くこと

- 何が変わり、読み手にどんな影響があるかを書きます。読み手は、利用者、成果物を見る人、そのリポジトリで次に作業する人や生成AIです。使い方・設定・出力・保存先が変わるなら、読み手がすること（移し方、作り直し方など）も書きます。
- 後で理由が要る変更（方針の決定、やめたこと、本人に確かめたこと）は、理由も書きます。
- commit messageの羅列や、作業の細かい記録で代えません。日々の追記（ノートの記録など）は1件ずつ書かず、構成・決まり・道具・成果物の変化を書きます。
- 個人の場所のパスや秘密情報は書きません。公開しないリポジトリでも、参考として共有することがあるためです。

## 4. 書き方

- 見出しは `# Changelog` とし、新しい項目を上に書きます。
- 版の番号があるリポジトリでは、版ごとに `## <版> - <YYYY-MM-DD>` の節を作ります。まだ出していない変更は `## Unreleased` に書き、版と日付が決まったときに、その版の節へ移します。決まっていない版の番号や日付は付けません。
- 版の番号がないリポジトリ（制作フォルダ、文書のリポジトリなど）では、変更した日ごとに `## <YYYY-MM-DD>` の節を作ります。
- 1つの節が長くなるときは、`###` で、成果物や作業の単位に分けます。
- スライドの番号やファイル名など、後の変更で指すものが変わる記録には、どの時点の番号・名前かを書きます。

## 5. 更新するとき

- 変更をcommitする作業の中でCHANGELOGも直し、同じcommitに入れます。
- 版を出す前や、まとまった作業を終える前に、CHANGELOGの内容と日付が実際の変更と合っているかを確かめます。
