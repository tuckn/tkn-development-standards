# YAML記述規約

日付・日時は **ダブルクォートで囲んだ ISO 8601 の文字列**、Windowsパス（URLスキーム付きの値を除く）は **シングルクォートで囲んだ文字列** として記述します。それ以外の文字列は、引用符なしで同じ文字列として読める場合は引用符を付けません。型の解釈が異なるツール間でも、値と意味を保って読み書きするための共通規約です。

## 1. 位置付けと適用範囲

本書は、CLIの設定ファイル、Markdown Frontmatter、テンプレート、READMEや仕様書に載せるYAML例に適用します。人による編集とプログラムによる生成の両方を対象とします。

[CLIリポジトリREADME執筆規約](readme-writing.md)は説明の構成と書き方、本書はYAMLの値・引用符・型の表記を定めます。ファイルの配置、必須項目、項目の意味は対象アプリケーションの仕様に従います。本書はPythonや特定のノート管理環境を前提としません。

本書の「必須」は共通の運用規約を示します。YAML言語そのものの必須構文とは区別します。外部サービスなどが別の型・形式を要求する場合は、その入出力仕様を優先し、例外と変換箇所を対象プロジェクトに記載します。

### 1.1. 用途ごとに定めること

値の書き方は、用途を問わず本書に従います。次の項目は、アプリケーションの設定ファイルやMarkdown Frontmatterなど、用途ごとの仕様で定めます。

- キー名の命名規則。例えば、アプリケーションの設定では `schema_version` のような `snake_case`、Frontmatterでは `schemaVersion` のような `lowerCamelCase` を選ぶ場合があります。
- 未設定値を `prop:` と `prop: null` のどちらで書くか（2.1）。
- 入れ子のマッピングや配列を使えるか（6章）。
- スキーマのバージョンを表すキー名と、その置き場所。
- 必須項目、項目の順番、項目の意味。

CLIの設定ファイルでの選択は、[Python CLI開発基本方針](python-cli-development.md)の「6.1.1 config schema version」「6.1.2 config property名」で定めています。

## 2. 値と引用符の基本ルール

次の例は表記の説明用です。キー名やその命名規則を、全アプリケーションの必須項目として定めるものではありません。

| 値の種類 | 標準表記 | 判断の基準 |
| --- | --- | --- |
| 日付 | `date: "2026-10-07"` | ダブルクォート必須。日付だけで分かる情報を保持する。 |
| 日時 | `created: "2026-10-07T09:30:00+09:00"` | ダブルクォート必須。新規記録ではタイムゾーンを含める。 |
| Windowsパス | `input_dir: 'C:\path\to\input'` | シングルクォート必須。バックスラッシュをそのまま記述する。 |
| URLスキーム付きの値 | `source: file:///C:/path/to/file.md`、`url: https://example.com/` | Windowsパスのシングルクォート必須規約から除外する。5章の規則に従う。 |
| その他の文字列 | `type: spec`、`status: draft` | 引用符なしで同じ文字列として読めれば、引用符なしを標準とする。 |
| 数字などに見える文字列 | `code: "00123"`、`label: "true"` | 数値・真偽値・nullと誤解される値はダブルクォートで囲む。 |
| バージョン文字列 | `schemaVersion: "1.0.0"` | 数値として扱わず、ダブルクォートで囲む。 |
| 配列などの構文に見える文字列 | `label: "[example]"` | 構造として解釈させず文字列を保つため、ダブルクォートで囲む。 |
| UUID | `id: 3f2b8c1e-9d4a-4e6b-8c2f-7a1d5e9b0c34` | ハイフン付きの標準形は、引用符なしを標準とする。 |
| ハッシュ・数字だけのID | `commit: "1234567"` | 値によって数値と解釈されるため、その項目の値をすべてダブルクォートで囲む。 |
| 数値・真偽値 | `count: 3`、`enabled: true` | 数値・真偽値として使う場合は引用符を付けない。真偽値は小文字の `true` / `false`。 |

値の表記は、次の順番で判断します。

1. 数値・真偽値として使う値には、引用符を付けません。未設定値は2.1に従います。
2. 日付・日時は、ダブルクォートで囲みます（3章）。
3. Windowsパスは、シングルクォートで囲みます（4章）。URLスキーム付きの値は含めません。
4. それ以外の文字列は、5章に従います。引用符なしで同じ文字列として読める値には、引用符を付けません。読めない値と、値によって数値などの形になる項目は、ダブルクォートで囲みます。

### 2.1. 未設定値・空文字・空配列

- 複数の値を指定できるプロパティと確定している場合、未設定時は空配列 `[]` を推奨します。例: `tags: []`、`inputs: []`。
- それ以外のプロパティや、単一値・複数値のどちらか未確定のプロパティでは、未設定値として `prop:` を許容します。プロパティ名だけから配列と推測して `[]` を設定しません。
- `prop:` はYAML上では `null` です。`prop: null` と同じ値です。表記の選択は対象プロジェクトで定めます。コロンの後ろの空白は不要です。
- 空の文字列を表す場合は `prop: ""` とします。未設定の `null` とは区別します。
- 数値・真偽値・日付・日時が未設定の場合も `prop:` を許容します。未設定を表すために `0`、`false`、現在日時を入れません。値のある日付・日時はダブルクォートで囲みます。
- 任意プロパティは、不要であればキー自体を省略してよいものとします。必須プロパティの有無や、未設定を許すかは対象スキーマに従います。

`null`、空文字 `""`、空配列 `[]`、キーの省略は別の状態です。既存値を機械的に相互置換しません。CLIや外部サービスで型・未設定値の契約が定められている場合は、その契約を優先します。

```yaml
# --- Empty and unset values ---
tags: []          # Multiple values are supported
inputs: []        # Multiple values are supported
description: ""   # Empty string
purchasePrice:   # Unset number
isConfirmed:     # Unset boolean
dueDate:         # Unset date
created:         # Unset creation time
customProperty:  # Value type or multiplicity is not yet defined
```

## 3. 日付・日時

### 3.1. 記録形式

- 日付は `YYYY-MM-DD` とします。
- 時刻まで記録する場合は `YYYY-MM-DDTHH:mm:ss±HH:mm` またはUTCの `YYYY-MM-DDTHH:mm:ssZ` とします。日付と時刻の区切りは大文字の `T` です。
- 秒未満が必要な場合は、小数点に続けて小数秒を記述できます。精度は対象アプリケーションが定め、表記統一だけを理由に桁数を丸めたり削除したりしません。
- 日付・日時の値全体をダブルクォートで囲みます。プロパティ名や、配列の内外を問いません。
- 時刻が不明な場合は日付だけにします。時刻やタイムゾーンを推測して補いません。時刻の一部しか分からない場合の保存方法は個別スキーマで定め、根拠のない `00` で既知の時刻に見せません。

```yaml
# --- Dates and times ---
date: "2026-10-07"
created: "2026-10-07T09:30:00+09:00"
updated: "2026-10-07T00:30:00.123456Z"
reviewDates:
  - "2026-10-07"
  - "2026-10-14"
```

新規に日時を生成する処理は、UTCかローカル時刻か、秒以下の精度をプロジェクト内で統一します。既存値の `Z` と `+00:00`、UTCと `+09:00` は、引用符の変更時には変換しません。時差や精度の正規化が必要な処理では、その目的と変換規則を別途定めます。

日時文字列に引用符を付けることと、暦として妥当かを検証することは別です。例えば `"2026-02-30"` はYAML文字列として読めますが、正しい日付ではありません。アプリケーションは項目の意味に応じて日付・タイムゾーンを検証します。

### 3.2. ダブルクォートを使う理由

YAML 1.1のtimestamp型では、引用符なしの日時を日時型として扱う規則があります。YAML 1.2のCore Schemaにはtimestamp型が含まれません。実際の解釈は利用するローダーとスキーマにも依存します。[YAML 1.1 timestamp仕様](https://yaml.org/type/timestamp.html)と[YAML仕様の変更点](https://yaml.org/spec/1.2.2/ext/changes/)を参照してください。

本書では、YAML上の値を文字列として安定させ、アプリケーションが必要な場面で日時に変換する方針を採ります。シングルクォートでも文字列として表せますが、日時はダブルクォートに統一します。明示的な `!!timestamp` タグは、この共通規約では使用しません。

Obsidianなどが読み込んだ文字列をアプリケーション側で日付プロパティとして扱うことと、YAMLローダーが日時型へ変換することは区別します。

### 3.3. 各日時項目の意味

`created`、`updated`、`published` などの意味や更新条件は、対象スキーマで定めます。引用符の規約は、値が「ノートの更新」「画像の生成」「公開」のどれを表すかを決めません。

ノート自身と、そのノートが参照するファイルや処理の日時は区別します。値を作れない場合、現在時刻を便宜的に入れず、空値・省略・エラーのどれを使うかを対象仕様に従って判断します。

## 4. パスとエスケープ

Windowsパスはシングルクォートで囲みます。ただし、`file:///`、`https://`、`http://` などのURLスキーム付きの値は、この規約の対象外です。Windows上のファイルを指す `file:///C:/path/to/file.md` もURLとして扱います。これらは5章の規則に従い、引用符なしで同じ文字列として読める場合は引用符を付けません。

Windowsパスにシングルクォートを使うのは、ダブルクォート内ではバックスラッシュがエスケープとして働き、パスの `\n` や `\t` などを意図せず解釈させないためです。シングルクォート内で文字 `'` を表す場合は、`''` と2つ重ねます。[YAML 1.2.2の引用符仕様](https://yaml.org/spec/1.2.2/#73-flow-scalar-styles)を参照してください。

```yaml
# --- Paths ---
input_dir: 'C:\path\to\input'
network_dir: '\\server\share\images'
owner_dir: 'C:\path\to\user''s images'
cover: "releases/photo.webp"

# --- URLs (not Windows paths) ---
source: file:///C:/path/to/file.md
url: https://example.com/
```

相対パスの基準が設定ファイル、作業ディレクトリ、アプリケーションのルートのどれかは、アプリケーション仕様で明記します。引用符は相対パスの基準を変えません。URLや文章の一部に日付が含まれていても、その値全体を日時として変換しません。

公開する設定例・README・テストには、実ユーザーの個人フォルダを使わず、上記のような汎用パスを使用します。

## 5. その他の文字列と識別子

日付・日時・Windowsパス以外の文字列の表記を定めます。判断の基準は、引用符なしで書いたときに、YAMLが同じ文字列として読むかどうかです。キー名からは判断しません。例えば、キー名が `type` でも、値が `true` なら真偽値として読まれます。

### 5.1. 引用符なしを標準とする値

引用符なしで同じ文字列として読める値は、引用符なしを標準とします。種別・状態などのあらかじめ決めた値、型名、slug、通常の文章などが該当します。

```yaml
# --- Plain strings ---
type: log
status: draft
format: webp
title: Weekly review notes
```

`type: "log"` も `type: log` と同じ値・同じ型を表す有効なYAMLです。引用符付きの入力をエラーにせず、新規生成・整形時に引用符なしへ揃えます。引用符だけの変更に伴う更新日時の扱いは、対象スキーマの契約に従います。

### 5.2. ダブルクォートで囲む値

引用符なしでは別の型・構造として読まれる値や、YAMLの構文と重なる値は、ダブルクォートで囲みます。

| 値の例 | 引用符なしで書いた場合 |
| --- | --- |
| `true`、`false`、`yes`、`no`、`on`、`off`、`y`、`n` | 真偽値として読まれる場合がある。`yes`・`on` などはYAML 1.2のCore Schemaでは文字列だが、YAML 1.1のローダーでは真偽値になる。 |
| `null`、`~` | nullとして読まれる。 |
| `123`、`00123`、`1.0`、`1e3`、`0x1F` | 数値として読まれる場合がある。`00123` は先頭の0が失われ、YAML 1.1のローダーでは8進数として83になる。 |
| `2026-10-11` | 日付として読まれる場合がある。日付として使う値は3章に従う。 |
| `[log]`、`{key: value}` | 配列・マッピングとして読まれる。 |
| `: ` または ` #` を含む値 | マッピングの区切り・コメントとして読まれるか、エラーになる。 |
| 前後に空白がある値 | 前後の空白が失われる。 |
| 空の文字列 | nullとして読まれる。空の文字列は `prop: ""` と書く（2.1）。 |

`- `・`? `・`: ` のように記号と空白で始まる値や、`,`、`#`、`&`、`*`、`!`、`|`、`>`、`%`、`@`、バッククォートで始まる値も、YAMLの記号として扱われるかエラーになるため、ダブルクォートで囲みます。判断に迷う値も、ダブルクォートで囲みます。

ダブルクォート内では、バックスラッシュがエスケープとして働きます。正規表現など、バックスラッシュをそのまま書く値には、4章のWindowsパスと同じ理由でシングルクォートを使います。

### 5.3. UUID・ハッシュなどの識別子

ハイフン付きの標準形のUUID（16進数を8-4-4-4-12桁で区切った形）は、YAML 1.1・1.2のどちらでも数値・日付・真偽値として読まれません。引用符なしを標準とします。UUIDの大文字・小文字は、引用符の整形だけでは変更しません。新規に生成する場合は、[RFC 9562](https://www.rfc-editor.org/rfc/rfc9562)に従って小文字で出力します。

値によって数値などの形になる識別子は、その項目の値をすべてダブルクォートで囲みます。ハイフンなしの16進数、コミットハッシュ、数字だけのID、先頭が0のコードが該当します。例えば、短いコミットハッシュの `1234567` は整数、`12e4567` はYAML 1.2では浮動小数点数として読まれます。引用符なしでも安全な値だけを選んで引用符を外すと、値を書き換えたときに型が変わるため、項目単位で表記を揃えます。バージョン文字列を常にダブルクォートで囲むのも、同じ理由です。

```yaml
# --- Identifiers ---
id: 3f2b8c1e-9d4a-4e6b-8c2f-7a1d5e9b0c34
commit: "a1b2c3d"   # Quoted even when the value would stay a string
sha256: "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"
code: "00123"
```

## 6. 構造・Frontmatter・コメント

- 新規ファイルは原則UTF-8とし、インデントはスペース2個を使います。既存ファイルの改行形式は、表記変更だけの作業では保持します。
- 同じマッピング内に重複キーを記述しません。
- 項目を意味のあるまとまりで並べます。順番は読みやすさの規約であり、通常のYAMLマッピングの意味に依存させません。
- YAMLでは必要な階層構造を使用できます。Frontmatterを読むアプリケーションに構造上の制約がある場合は、その仕様に従います。
- Markdown Frontmatterの開始・終了はそれぞれ独立した行の `---` とし、終了行と本文のH1の間に空行を1行設けます。
- 生成するFrontmatterの区切りコメントは英語とします。例: `# --- Dates and times ---`。既存の利用者コメントは保持します。
- 値の順番や区切りコメントを利用者が変える必要がある場合は、外部テンプレートで管理します。引用符と型は値をシリアライズする処理で保証します。

## 7. 実装・既存ファイルの移行・検証

出力処理は日時を文字列として渡し、ダブルクォートのスタイルを明示します。標準の日時オブジェクトをそのまま渡し、ライブラリの既定出力に任せるだけでは、この表記規約を保証できません。

5章の判断をライブラリの既定出力に任せる場合は、出力側と読込側でYAMLの版が異なっても型が変わらないかを確認します。YAML 1.2を前提にした出力では、YAML 1.1で真偽値になる `yes`・`on` などに引用符が付かない場合があります。逆に、YAML 1.1を前提にした出力では、YAML 1.2で数値になる `12e4567` などに引用符が付かない場合があります。5.3で項目単位にダブルクォートで囲むと定めた識別子は、値ごとの判断に任せず、出力処理で引用符のスタイルを指定します。

スキーマをJSONで記述する場合、JSON内のキー・文字列にはダブルクォートが必要です。これはYAMLの出力でダブルクォートを付けるという指定ではありません。値の型と、YAMLへの出力時の引用符スタイルは別に定めます。

既存の引用符なし日時を受け付ける場合は、読み込み時の日時型変換によって、小数秒の精度、タイムゾーン、元の表記を失わないようにします。日時の値を一度低精度のオブジェクトに変換してから引用符を付けても、失った情報は戻せません。

既存ファイルを一括変更する場合は、次の順番で確認します。

1. 対象と変更内容をdry-runで列挙し、日時以外の値を誤認していないか確認します。
2. 原本をバックアップし、適用直前にも対象が別の処理で編集されていないことを確認します。
3. 引用符だけの移行では、日時の値、本文、コメント、ID、項目順を保持します。表現だけを変更する移行では、対象仕様に別の規則がなければ `created` / `updated` 自体も保持します。通常のCLI更新時の更新日時の扱いとは区別します。
4. 出力を再読込し、日付・日時が文字列であることと、値・オフセット・小数秒の保持を確認します。
5. 同じ処理を再実行しても差分が発生しないことを確認します。

テストでは、日付だけ、UTCの `Z`、正負のオフセット、小数秒、既存の引用符なし・シングルクォート、独自プロパティ、配列、空値、`yes` などの真偽値に見える文字列、UUID・ハッシュなどの識別子を含めます。生成例と文書内のサンプルも同じ規約にそろえます。全体への単純な文字列置換で、本文やURLまで変更しないようにします。
