# CLIリポジトリREADME執筆規約

この文書は、初めて CLI リポジトリを見る人が「何ができるか」を理解し、準備・実行・結果確認まで進める README を書くための共通の執筆規約です。
既存の CLI リポジトリと、これから作成する CLI リポジトリの両方に適用します。
README から参照する利用手順、設定リファレンス、運用ガイド、仕様書、設計・検証資料にも、役割に応じて配置・説明・更新の指針を適用します。
README、CHANGELOG、関連文書を、人がコード全体を読まなくても、成果物・動作・設計理由・変更内容を理解し、確認の根拠へ到達できる場所として維持します。
人と生成 AI のどちらが執筆しても、読みやすさと事実の正確さを両立させることを目指します。

**品質の基準は、文字数や章数ではなく、読者が必要な判断と作業を自力で行えることです。**

情報を載せる前に「この説明は、読者のどの判断・操作に必要か」を確認します。
正しい事実でも、現在の読者に必要なければ省きます。必要な情報は、それを使う段階に置きます。
構成例や確認項目を埋めること自体を目的にしません。

## 1. 位置付けと適用範囲

本書は、実装言語に依存せず、README・CHANGELOG・関連文書の役割と配置、情報の並べ方、
説明の粒度、表現、更新・確認の手順を定めます。
Python CLIでは、[Python CLI開発基本方針](python-cli-development.md)の「11. README」と併用します。
インストール、設定、CLIの動作、データ保護などの技術要件は、対象言語の開発方針と対象リポジトリの仕様を参照します。
本書の適用だけでPython・uvの採用を要求するものではありません。

本書を共通の正本とし、各 CLI リポジトリに同じ執筆規約の全文コピーやリポジトリ専用の執筆規約を作成する必要はありません。
リポジトリ固有の例外や追加条件だけを、そのリポジトリの文書へ記載します。
生成 AI へ依頼するときは、本書を添付するか、実際に読める参照先を渡します。
公開リポジトリに、個人固有のファイルシステムの絶対パスを記載しません。

- README の新規作成・大幅な改訂では、本書全体を確認して構成から設計します。
- 日常の修正では、関連する節と完了前の確認項目を適用します。
- 既存リポジトリへの適用では、有用な説明・互換性・安全条件を保持して再構成します。
- README の書き方が同じでも、コマンド・既定値・対応範囲は各 CLI の実装で確認します。

- 個別依頼で指定された目的・対象・変更範囲を優先し、適用される基本方針と組み合わせます。
- 特定のリポジトリ名、コマンド、保存構造、外部サービスを、他のリポジトリに共通する要件にしません。
- CLI 以外のライブラリ、サービス、インフラなどにも、読者を案内する原則と文体の指針を適用できます。
- 文書の構成は役割に合わせます。仕様書や運用手順書に、README と同じ章構成を要求しません。
- `AGENTS.md`、変更履歴、生成物、引用資料は、それぞれの用途や管理方法を尊重します。本書の適用を理由に一律に書き換えません。

規範用語は、基本方針と同じ意味で使用します。

| 表現 | 適用の強さ |
| --- | --- |
| 必須 | 原則として満たします。満たせない場合は理由を明記します。 |
| 原則 | 通常は採用します。対象の性質に応じた例外を認めます。 |
| 任意 | 読者の理解や操作に役立つ場合に採用します。 |

以下の指針は、対象となる機能や説明が存在する場合に適用します。
該当しない項目のために、機能・文書・空の章を追加する必要はありません。
参考にする優れた文書も、構成や表現の実例です。
実例にある機能や数値を転用したり、実例の記述を仕様や本書より優先したりしません。

## 2. 読者と品質の基準

README の主な読者は、そのリポジトリの用語・設計・開発経緯を知らない利用者です。
開発知識がある読者でも、プロジェクト固有の前提を共有しているとは考えません。
時間を置いて戻ってきた利用者、引き継ぐ人、作業を補助する生成 AI も、同じ文書から必要な情報を探せるようにします。

| 原則 | 文書で実現すること |
| --- | --- |
| 結果から説明する | 冒頭で用途・入力・得られるものを示し、利用者にとって何ができるようになるかを伝えます。実例は、その理解を助けるものを選びます。 |
| 読者が知る順に並べる | 利用判断、準備、実行、結果確認をつなぎ、詳細は必要なときに参照できるようにします。 |
| 関係を明示する | 用語の意味、選択肢の違い、設定と動作の対応、処理の担当範囲を分かる形にします。 |
| 判断に必要な具体性を持たせる | 「上限」「保存」「再実行」などについて、何の単位か、どこに残るか、何が起きるかを書きます。 |
| 現行の事実を保つ | 実装・仕様・確認結果に照らして記述し、未確認事項や説明用の例を区別します。 |
| 更新後も読みやすさを保つ | 新しい説明を適切な場所へ統合し、古い説明・重複・リンクを一緒に見直します。 |

README と直接リンクした文書から、少なくとも次の問いに答えられることを必須とします。

1. 何のためのリポジトリで、自分の用途に使えるか。
2. 何を用意し、何を設定すれば始められるか。
3. どの操作を、どの順に行うか。
4. 何が作成・変更され、結果をどこで確認するか。
5. 再実行や失敗時に何が起き、次に何をすればよいか。
6. 詳細な仕様や、変更・保守の手順をどこで調べるか。

## 3. 情報の配置と章構成

### 3.1. 文書の役割を決める

説明の置き場所は「誰が、何を確認するために読むか」で決めます。
`README.md` と `CHANGELOG.md` はリポジトリ直下に置き、詳細文書は原則として `docs/` 直下へ、内容が分かるファイル名で配置します。
文書の役割を区別するために、分類用のフォルダを先に作る必要はありません。

#### 文書名と読者の問い

以下は役割と配置の例です。すべての文書を作る要件ではなく、必要な説明だけを用意します。ファイル名は原則として小文字の kebab-case とし、README・CHANGELOG などの定着した名前を除きます。

| 配置先の例 | 読者が確認すること |
| --- | --- |
| `README.md` | 何のための CLI か。入力と得られる結果、対象範囲、準備、最初の実行、日常利用、詳細への入口は何か。 |
| `CHANGELOG.md` | 以前のバージョンから何が変わり、利用者にどのような影響・対応があるか。 |
| `docs/specification.md` | 入出力、処理規則、識別子、互換性、副作用、保護条件、対応範囲として、何を契約するか。 |
| `docs/architecture.md` | 全体構成、処理の流れ、責務分担、連携境界はどうなっており、なぜその設計を選んだか。 |
| `docs/configuration.md` | 設定項目の意味・型・既定値・優先順位・検証条件は何か。何を変えると動作がどう変わるか。 |
| `docs/operations.md` | 日常の更新、再実行、中断からの復旧、移行をどの順に行い、結果をどう確認するか。 |
| `docs/cli-output.md` | 標準出力・標準エラー・終了コード・JSON の項目や意味について、何が保証されるか。 |
| `docs/validation.md` | どの方法・条件で何を検証し、何が未検証か。対応する検証結果をどこで確認できるか。 |

学習用の教材が必要なら `docs/tutorial-<topic>.md`、開発環境・テスト・変更手順を独立させるなら `docs/development.md` や `CONTRIBUTING.md` など、内容と用途が分かる名前を選びます。
README の「関連ドキュメント」などから、「設定を調べる」「処理仕様を確認する」「復旧する」のように読む目的を添えて案内します。文書数が少なければ、別の文書一覧ファイルは不要です。

#### 用語と格納範囲

`specification` は意図する動作・形式・制約を定める文書、`reference` は項目ごとの正確な情報を引く文書、`guide` は目的を達成する手順を案内する文書を指します。
`handoff` は、ある時点の状況を次の担当者へ伝える文書です。これらは分類の観点が異なり、一つの文書が複数の役割を持つ場合があります。
`reference` を「参照できるものすべて」の格納先にせず、これらの名前を持つフォルダの作成を必須にしません。外部の参考文献や引用元は、関連文書の出典・参考文献節で示します。

#### 正本と分割の判断

- 詳細の正本を一つに決め、他の文書には必要な要約とリンクを置きます。例えば CLI 出力契約を `cli-output.md` に分けた場合、`specification.md` に同じ詳細を複製しません。操作前に必要な注意の要点は、その操作の近くにも残します。
- 詳細情報を README に含めること自体は問題ありません。初回利用を妨げるか、目的の情報を探しにくいか、独立して参照・更新する必要があるかで、再配置や分割を判断します。文字数や文書数だけで機械的に分割しません。
- 一つの主題を理解するために仕様と手順の両方が必要なら、同じファイル内で見出しを分けても構いません。各節の役割と正本を明確にし、分類名に合わせるためだけに説明を細分化しません。
- 関連文書が増え、まとまりを設けた方が探索・更新しやすくなった場合だけサブフォルダを追加します。用途と格納範囲を README またはそのフォルダの案内に記載し、文書のない分類のために空のフォルダを作りません。
- 既存の `reference/`・`specs/`・`guides/` などを一括で改名・移動する必要はありません。依頼された対象と影響を確認し、有用な説明を保持して段階的に適用します。移動時は8.3に従い参照も更新します。

#### 現行文書と時点を持つ記録

仕様・設定・運用・構成の説明は、対象版の現在の状態に合わせて維持します。未実装の仕様や提案は、その状態を明記し、現在使える機能として案内しません。記述と確認根拠の扱いは7章に従います。

判断記録、実施した検証の結果、引き継ぎ文書は、日付・対象版・当時の状態を持つ記録として扱います。過去の記録を最新の説明として読ませず、現行文書との関係や後続の記録への参照を示します。
共有する設計判断が増えた場合は `docs/decisions/`、共有する検証結果が増えた場合は `docs/validation/` などにまとめられます。`validation.md` には検証方法・現在の確認範囲と、対応する結果への参照を置きます。少数ならファイル内で方法と日付付きの結果を分けても構いません。

引き継ぎ文書は、作成時点の実装状況、未完了事項、次の作業、根拠への参照を伝えます。採用した仕様・設計理由・必要な手順を引き継ぎ文書だけに残さず、現行文書へ反映して案内します。
私的な作業再開メモや実機検証記録は、この文書群で採用するローカル作業資料の区分に従って `.local/state/<datetime_work-id>/` に置きます。再開用資料・保持する生成物・バックアップは対応する `.local/data/<datetime_work-id>/` に置き、共有文書へ個人の実データや私的な作業記録を無条件に転記しません。`/.local/` をGit管理対象外とし、保持資料を通常の一時ファイルcleanupで削除しません。

### 3.2. 初回利用と参照の読み方を用意する

README の前半は上から順に読み、最初の結果まで進める構成にします。
後半はコマンドや作業目的から、必要な情報を直接探せる構成にします。
長い文書では、冒頭に「初めて使う場合に読む範囲」と「必要時に参照する範囲」を短く案内します。

セットアップが複数の手順に分かれ、最初の結果まで距離がある場合は、概要の直後にクイックスタートを置くことを任意で認めます。
クイックスタートには、代表的な前提（例えば既定の接続先が認証済みであること）を1文で示し、導入から最初の結果までのコマンドを1つのコードブロックに並べます。
各コマンドにはコメントで目的を添え、完了後に結果を確認する場所と、外部送信・費用などの実行前の条件を示します。
クイックスタートは詳細なセットアップの代わりではありません。前提が異なる読者を、詳細な手順へリンクで案内します。

標準的な CLI では、次の順序を原則とします。

| 順序 | 内容 | 読者が分かること |
| --- | --- | --- |
| 1 | 概要と成果が分かる短い例 | 何を入力し、何が得られ、どう使えるか |
| 2 | 利用判断に必要な対象範囲・用語・全体像 | 自分の用途に合うか、主要な概念がどう関係するか |
| 3 | セットアップ | 必要環境、通常のインストール、最小限の設定 |
| 4 | 最初の実行と結果確認 | 操作の順序、処理対象、作成物、確認方法 |
| 5 | 日常利用 | 更新、再実行、中断・再開、必要に応じた定期実行 |
| 6 | コマンド一覧 | 目的に合うコマンドと、詳細の参照先 |
| 7 | 詳細 | 設定、処理、保存構造、制約、結果やログの解釈 |
| 8 | 保守・移行、開発・検証、関連資料 | 利用を続ける方法、変更する方法、より詳しい情報 |

これは情報の順序を示すもので、各行を独立した章にする必要はありません。
「使い方」の下にセットアップと実行をまとめても、別の章に分けても構いません。
概要は見出しなしを基本とし、内容に応じて「これは何か」などの見出しを付けても構いません。

前半の用語や図は、利用判断と最初の操作に必要なものに絞ります。
長い用語集、内部ファイルの一覧、詳細な処理シーケンスは後半へ置きます。
初回の出力を得る前に、内部構造をすべて学ぶ必要がある構成にしません。

ライブラリでは最小の利用コード、サービスでは利用開始、インフラでは管理対象・現在の状態・運用開始の手順を中心に再編します。
いずれも「用途を理解する → 最初の作業を行う → 必要な詳細を調べる」という流れを保ちます。

### 3.3. CLI README の構成例

標準的な CLI では、次の構成を出発点にします。
各見出しの内容は、前節の「読者が分かること」を満たすように書きます。
以下は日本語で示した構成例です。実際の見出しと本文は、9章で選んだ言語に合わせます。

```text
# <用途が分かるツールの表示名>

<補助言語版がある場合はそのリンク>
<初回利用と参照情報の読み方の案内>

## 1. これは何か
### 1.1. 得られる結果の例
### 1.2. 対象範囲
### 1.3. 最初に必要な用語
### 1.4. 全体像

## 2. セットアップ
### 2.1. 前提
### 2.2. インストール
### 2.3. 設定ファイルの作成
### 2.4. 最小限の設定と確認

## 3. 実行する
### 3.1. 最初の実行と結果確認
### 3.2. 日常の更新
### 3.3. 中断と再開

## 4. コマンド一覧
## 5. 設定
## 6. 保存構造・処理の詳細
## 7. 対応範囲と制限
## 8. 更新・保守・移行
## 9. 開発と検証
## 10. 関連ドキュメント
```

クイックスタートを置く場合は、「これは何か」と「セットアップ」の間に置きます。
独自の用語が少なければ用語表を本文へまとめ、保存を行わない CLI では保存構造の章を省略します。
設定、日常の更新、中断・再開なども、対象に存在する機能だけを説明します。
定期実行が主要な用途なら「実行する」に追加し、詳細が長ければ運用ガイドへ案内します。
初回利用で知る必要のある保存領域の役割は、概要で短く説明しても構いません。
見出し名や章番号の一致より、「何かを理解する → 実行する → 結果を確認する → 詳細を調べる」という順序を優先します。

### 3.4. 見出しと参照先を分かる形にする

- 文書タイトルにはツールの表示名を使い、名前だけで用途が伝わらなければ短い説明を添えます。実行コマンド名は、使い方の中で示します。
- 見出しは「保存先を変更する」「結果の読み方」など、内容や読者の目的が分かる名前にします。
- コマンドや設定キーを見出しに含める場合も、必要に応じて文書の言語に合わせた説明を添えます。
- コマンド一覧では、利用者の目的、コマンド・主な引数、詳細へのリンクを対応させます。すべてのオプションを列挙する必要はありません。通常利用と保守・移行の用途が分かるようにします。
- 手動の目次は作成しません。GitHub をはじめ主要なビューワーは見出しから目次を自動生成するうえ、手動の目次は見出しの変更のたびに更新が必要で、リンク切れの原因になるためです。代わりに、冒頭で「初めて使う場合に読む範囲」と「必要時に参照する範囲」を短く案内します。
- 章番号は、長い文書の案内や相互参照に役立つ場合に採用します。番号の有無より、階層と参照の正確さを優先します。
- 章を案内するときは、番号だけでなく見出し名とリンクを使います。
- 詳細を説明する場所は原則として1か所に定め、概要やコマンド一覧から参照します。
- 操作直前の重要な注意や、理解に必要な短い要約は再掲できます。詳細な規則を複製する場合とは区別します。

## 4. 手順と仕様の説明

### 4.1. 最初の結果までをつなげる

最初の利用手順では、代表的な1つの方法を最後まで示します。
複数の導入方式や高度な設定を、途中で次々に選ばせないようにします。

1. 対応 OS、実行環境、必要な入力、認証などの前提を示します。
2. 作業フォルダと通常のインストール方法、導入できたことの確認方法を示します。
3. 設定ファイルの作成方法、編集する場所、最初に変更する項目、設定の確認方法を示します。
4. 利用者が目的とする処理を実行します。
5. 得られるファイルや表示と、正常に完了したことの確認方法を示します。

設定ファイルの作成と、データ保存領域などの初期化が別操作の場合は、それぞれの役割を短く説明します。

各手順の説明は、原則として「何をするか → 実行例 → 何が起きるか・何を確認するか」の順にします。
インストール、設定ファイルの作成、設定の編集、処理の実行は、目的ごとに説明とコードブロックを分けます。
結果の確認を案内するときは、確認する目的と判断基準を示し、自動検査と利用者による任意の確認を区別します。
前提となるファイルや設定が前の手順で用意されているか、通して確認します。

本書を適用するすべての CLI では、`--help` と `--version` を必ず実装します。実装言語や業務機能の有無にかかわらず、この2つを必須オプションとします。

| 必須オプション | 動作 |
| --- | --- |
| `<command> --help` | CLI の使い方、利用可能なコマンド・オプションを表示します。 |
| `<command> --version` | 実行中の CLI のバージョンを表示します。表示値はパッケージのバージョン情報と一致させます。 |

どちらもサブコマンドや必須引数を追加せず単独で実行でき、設定・認証が未完了でも表示して正常終了するようにします。データ取得・生成 AI 呼び出し・ファイルへの書き込みは行いません。
README のインストール確認には `--version` の実行例を必ず載せ、インストール済みのバージョンが表示されれば導入できたと判断できることを説明します。
`--help` は、コマンド一覧や引数の確認方法として本文で案内します。インストール確認のコードブロックに含めるかは任意です。
未実装の場合は実装が必要な差として報告し、README に記載するだけで要件を満たしたことにしません。実装の変更は依頼された範囲に従います。

基本方針を適用する Python CLI では、作業フォルダへの移動、通常の `uv tool install .`、CLI の `--help` と `--version` による確認を含めます。
更新後の `--reinstall` は保守、editable インストールは開発の説明に置きます。
他の技術構成へ、このツール名やインストール方式をそのまま要求しません。

複数の処理段階がある場合は、段階・コマンド・得られるものを対応させ、生成 AI や外部サービスを使う段階を明示します。
初回と日常でコマンドや処理対象が異なる場合は、分けて説明します。
初回の取り込み範囲、初期化日時、待機時間、対象がない場合の動作など、最初の結果が得られるかに関わる条件は前半にも残します。
主要コマンドが自動で行う補助処理を、利用者が別途実行する必須手順として列挙しません。
任意の後続処理や別ツールへの連携は、初回の完了条件と区別します。

### 4.2. コマンドは動作と結果を説明する

主要コマンドについて、次の情報を基本手順・共通説明・詳細説明を合わせて確認できることを必須とします。
すべてを各コマンドの直下へ繰り返す必要はありません。

| 観点 | 説明する内容 |
| --- | --- |
| 目的と入力 | 何のための操作か、どのデータを対象にするか、省略時は何を選ぶか |
| 出力と変更 | 何を作成・更新・削除するか、どこに保存するか |
| 実行条件 | 必要な設定・認証、前の処理が必要か |
| 副作用と保護 | 通信、外部送信、費用、上書き、保護の解除条件 |
| 再実行 | スキップ、上書き、再生成、中断後の再開の条件 |
| 結果確認 | 表示、成果物、ログ、レポート、終了コードの意味と確認方法 |
| 実行例 | 代表的な例と、必要な引数・オプションの位置 |

出力形式、標準出力と標準エラーの使い分け、終了コードは、現在の実装に合わせて説明します。
基本方針と実装に差がある場合は、文書だけを理想の動作に書き換えず、差を作業結果として報告します。

通常実行と `--dry-run` の違いは、最初の実行前に短く示します。
認証・通信・生成 AI 呼び出し・ファイル作成の有無などの詳細は、共通説明へまとめます。
dry-run の通信や認証の可否を、別のリポジトリの例から推測しません。
未対応のコマンドに、文書上だけで `--dry-run` を追加しません。
通常の preview は代表的なコマンドで示し、すべての手順に dry-run と本実行を重ねて載せる必要はありません。
削除や保護解除など、操作前の確認が重要な手順では preview と本実行を併記できます。
`--full-output`、`--quiet`、`--verbose` なども、共通の動作は集約し、各コマンド固有の違いだけを補足します。

利用判断や実行前に必要な外部送信・費用・削除・上書きの条件は、詳細へのリンクだけで済ませず、その操作の近くにも要点を書きます。
注意は、対象と条件、起きること、利用者の対応を具体的に示します。
費用は、どの処理で発生するかを先に説明し、dry-runなどの例外を後に続けます。
実際の判断に関わらない一般的な注意書きを大量に追加しません。

### 4.3. 設定は「何を変えると、何が変わるか」を示す

設定例には、設定ファイル全体なのか、一部の抜粋なのかを明記します。
抜粋には追加・変更する位置と、他の設定を保持することを示します。
「最小構成」と呼ぶ例は、前述の準備と指定値の置き換えを済ませれば、そのまま利用できる内容にします。

設定を参照する箇所では、次の情報を必要に応じて表や例にまとめます。

- 設定キー、意味、必須かどうか、既定値、許容値。
- 単位と適用範囲。例えば、秒か分か、1ファイルか1回の実行全体か。
- 省略時と、空文字・空の一覧・`null` などを明示したときの違い。
- 設定の優先順位、相対パスの基準、有効な設定の確認方法。
- 設定変更が出力、保存先、再処理、途中結果の再利用に及ぼす影響。

すべての章で同じ既定値を繰り返す必要はありません。
既定値を管理する説明先を決め、簡易説明・設定例・同梱設定との一致を確認します。
例示値、実装の既定値、外部サービスの制約値、推奨値を区別します。

### 4.4. 出力・保存・運用を利用者の判断につなげる

生成物はファイル名だけでなく、その役割と利用方法を説明します。
利用者が目的とする成果物と、実行状況を報告するログ・JSONなどを区別します。
表示や保存に触れる場合は、コンソールに表示するのか、どのファイルに保存するのかを明確にします。
複数の保存領域がある場合は、何を保存し、どれを保持すべきか、失うと何が起きるかを示します。
再作成できるデータでも、再処理に必要な元データ・時間・費用の条件があれば補足します。
特定の領域数や命名方式は要求しません。

ログやレポートの例は、表示の意味と次の操作を結び付けます。
見積もり、実測値、上限、不明値を区別し、数値の単位・集計範囲・成立条件を示します。
不明をゼロと解釈させたり、一部の成功を全体の完了と誤解させたりする説明を避けます。

対応範囲は「対応」「未対応」「未検証」を区別します。
自動処理を説明する場合は、CLI自体が常駐監視するのか、起動時に一度処理するのかを先に示し、その後に外部スケジューラによる定期実行を案内します。
失敗・未完了・処理対象なしの区別が操作に影響する場合は、代表的な状態と確認先・再開方法を説明します。

## 5. 用語と文体

### 5.1. 用語は理解するために必要な場所で定義する

- 独自の用語は、初出の近くで日常的な言葉に結び付けます。例えば「処理を再開するための記録（state）」と説明します。
- 少数の用語は本文で定義します。繰り返し参照する用語や混同しやすい概念が多い場合は、用語表にまとめます。
- 入力元と処理方式、設定名とモデル名など、似て見えて独立している概念は、何を変えると何が変わるかで区別します。
- 同じ語が複数の意味で使われる場合（例えば、要約の形式を選ぶプロファイルと接続先を選ぶプロファイル）や、設定ファイルが複数の層に分かれる場合（例えば、このツールの設定と、共有ライブラリの設定）は、1つの比較表にまとめます。列は「種類・設定する場所・それで選ぶもの・その実行だけ変える方法」のように、読者が選択や変更をするときの観点でそろえます。個別の説明の中で1つずつ注意するより、並べて見せた方が違いが伝わります。
- 用語表で定義した語でも、説明なしに略記や別名へ切り替えません。
- 識別子は正確な綴りを保ち、本文では選んだ言語で自然な文章を書きます。日本語の文書で、一般的な語まで英語へ置き換える必要はありません。
- 「入力フォルダ」などの説明がどの設定を指すか迷う場合は、初出で設定キーと対応させます。

### 5.2. 一度読んで関係が分かる文章にする

- 文体は文書内で統一します。利用者向けの日本語文書では「です・ます」を原則とします。
- 1段落は1つの主題にし、要点を先に述べてから条件や理由を補足します。
- 1文で複数の条件・結果・例外を扱い始めたら、文や箇条書きに分けます。日本語では80字程度を見直しの目安にできますが、字数のために意味を欠落させません。
- 主語・対象・条件が曖昧な箇所を補います。すべての文で自明な主語を繰り返す必要はありません。
- 「適切に処理します」「検証済み」など、内容の分からない要約語で済ませず、読者に必要な動作や検査範囲を具体化します。
- 「従来どおり」「今回対応しました」「ご要望に従い」など、開発経緯や会話を知らないと分からない表現を現行仕様の説明に残しません。
- 否定は、対象外や保護条件を理解するために使います。初見の利用者の判断に関わらない他製品名や、「不要」「行わない」の列挙は省きます。
- 括弧書きが続く場合は、独立した文・注記・表へ整理します。

### 5.3. Markdown のソースも読みやすくする

- 日本語の本文は、原則として1文1行で書きます。文の途中に固定幅の改行を入れません。
- 同じ話題の文は空行を挟まずに続け、話題が変わる位置で空行を入れて段落を分けます。
- 表のセル、コード、リストの構造、引用元の書式は、それぞれに必要な形式を優先します。
- 見出しの前後、リストやコードブロックの前後には、Markdown の構造が明確になる空行を入れます。
- コード、設定キー、コマンド、パス、識別子はバッククォートで囲みます。
- 日本語と半角英数字の間の空白、数字・単位・表記揺れは文書内で統一します。コード内の綴りは変えません。
- 箇条書きは同じ観点・同じ粒度でそろえます。太字は要点や操作前に必要な条件に絞ります。
- 操作の直前に読むべき注意は、GitHub のアラート記法（`> [!NOTE]`、`> [!IMPORTANT]`、`> [!WARNING]` など）で本文から切り離して目立たせることを原則とします。この記法は Obsidian のコールアウトとしても表示されます。
  - `WARNING`：上書き・削除・編集内容の置き換えなど、取り消せない変更。
  - `IMPORTANT`：外部への送信や費用の発生など、実行前に知っておくべき条件。
  - `NOTE`：動作確認の範囲や、自動検査で保証されない範囲などの補足。
- アラートは、実際に判断を変える注意に限って使います。多用すると本当に重要な警告が埋もれるため、1つの節に続けて置かず、一般的な注意書きには使いません。

### 5.4. 説明を具体化する例

次の改善例は、書き方を示す架空の仕様です。
実際の文書では、確認した動作に置き換えます。

| 説明が不足した表現 | 改善例 | 明確にしたこと |
| --- | --- | --- |
| 変更すると再生成されます。 | 出力言語を変更すると、次回の実行で既存レポートを作り直します。 | 変更する設定、対象、実行時点 |
| 上限は30です。 | 1回のコマンド実行で、外部 API を最大30回呼び出します。 | 単位と適用範囲 |
| 結果を確認してください。 | 完了時に表示されたレポートを開き、「失敗件数」が0であることを確認します。 | 確認先と判断基準 |
| cache は削除できます。 | 途中結果の cache は削除できます。次回は元データから再処理するため、時間と費用がかかります。 | 再作成の条件と影響 |
| バージョン2で失敗時の処理を改善しました。 | 処理に失敗すると、完了済みの出力を残して停止します。次回の実行は未完了分から再開します。 | 現行の動作と次の操作 |
| 出力スキーマ 1.1 のレポートを、スキーマ 1.2 で作り直すには `--force` が必要です。 | 更新で出力の形式が変わった場合、既存レポートを新しい形式で作り直すには `--force` が必要です。 | 特定の版の変遷ではなく、どの版でも成り立つ条件 |
| 保存の仕組みは3段階です。 | 取得・整形・生成の結果を段階ごとに保存するため、途中で失敗しても完了した段階から再開できます。 | 構成の理由と、それで利用者ができること |

## 6. 実例・表・図・リンクの使い分け

### 6.1. 実例で完成形を見せる

早い段階の例は、利用者が目的とする成果を伝えるために置きます。
生成文書の抜粋、画面、処理前後の違いを説明する短い文章など、用途に合う形式を選びます。
ファイル名の変化や保存先だけで済ませず、何ができるようになるかを示します。
処理件数のJSONやログは、利用者の目的がその出力自体である場合を除き、実行結果を読む箇所で扱います。
抜粋を載せる場合は、何の抜粋か、どこを見ればよいかを説明します。

実測・実出力、匿名化した実例、架空の説明例、表示を省略した抜粋を区別します。
サンプルがあることだけを、機能が実装されている証拠にしません。
個人の実パス、認証情報、非公開データを掲載せず、例全体で架空の名前やパスを統一します。
匿名化や省略によって、形式や項目の関係を壊さないようにします。

### 6.2. 表・箇条書き・図を目的に合わせる

| 伝えたいこと | 向いている形式 |
| --- | --- |
| 目的、理由、因果関係、補足 | 短い段落 |
| 順序がある操作 | 番号付きリスト |
| 順序を持たない条件や注意 | 箇条書き |
| 選択肢、設定と既定値、状態と対応、変更と影響の比較 | 表 |
| 複数の構成要素の関係、処理の流れ、やり取り | 図 |
| 入力方法や得られる結果 | コード・設定・出力の実例 |

表は、同じ観点で比較できる情報に使います。
長い説明を各セルへ詰め込む場合は、列を絞るか説明を表の外へ出します。
散文を機械的に表へ変換したり、表を置くこと自体を要件にしたりしません。

構成要素の関係や処理順序の図は、原則として GitHub で表示できる Mermaid を使用します。
処理の流れには `flowchart`、時系列のやり取りには `sequenceDiagram` など、目的に合う種類を選びます。
ノード ID と表示ラベルを分け、ラベルを短く保ち、記号・空白・括弧などを含むラベルは引用符で囲みます。
文字幅や表示環境によって崩れる、位置合わせに依存した複雑なアスキーアートは避けます。
全体像の図には主要な入出力と担当範囲を示し、詳細な内部処理の図とは分けます。
処理順序を示す図では、処理を動詞で表し、分岐には条件を示します。処理対象・保存先・担当を含める場合は、処理や判断と見分けられるラベル・形状・グループを使います。
矢印がデータの流れ、実行順序、参照関係のどれを表すか、読者が判断できるようにします。
図で示す自動処理と、利用者が別途行う操作を混同させません。

簡易的なフロー図では、処理を長方形、データを円筒形で表します。
円筒形はデータベースに限定せず、ログ、JSON、Markdownなどの保存データにも使います。
Mermaidでは、処理を `Process["データを変換する"]`、データを `Data[("変換後のデータ")]` の形で記述します。
図の導入文や凡例に「長方形は処理、円筒形はデータ」と明記し、同じ図の中で使い方を統一します。

図には目的を示す短い導入文と、図だけでは分からない条件・注意を添えます。
図と本文の併記は許容し、重要な情報を図だけに閉じ込めません。
同じ詳細を長い本文で繰り返すことは避けます。
単一の事実や単純な1操作のために、形式的な図を追加する必要はありません。

### 6.3. コード例は実行条件まで含める

- 特定のシェルに依存しないコマンド例では、コードフェンスの言語を原則として `shell` にします。汎用的な表現と、VS Code での構文の色分け（シンタックスハイライト）を両立させるためです。
- 実行場所は「ターミナル」「コマンド入力画面」などと表現し、必要がなければ PowerShell や Bash などの特定のシェルに限定しません。
- シェル固有のコマンド・変数・構文が必要な例では、対象シェルを明記し、`powershell` や `bash` など実際の内容に合う言語を指定します。言語指定だけを `shell` に変えて汎用的な例として扱いません。
- `console` はプロンプトや出力を含む端末の記録を示す場合に使い、コピーして実行するコマンド例とは分けます。設定やプログラムには `yaml`、`json`、`python` など、内容に合う言語を指定します。
- 表記の汎用化と動作確認の範囲は区別します。未検証の OS やシェルで動作すると断定せず、例のパス形式や実際に確認した環境を必要に応じて明記します。
- コピー対象のコマンドには、入力不要なプロンプト記号や実行結果を混ぜません。
- 対象 OS・シェル、作業フォルダ、オプションの位置、空白を含むパスの引用を確認します。
- YAML例では日時をダブルクォート、Windowsパスをシングルクォートで囲みます。型・エスケープ・既存データの保持などの詳細は、[YAML記述規約](yaml-style.md)に従います。
- 汎用的なコマンド例は、原則として1コマンドを1行に書きます。シェル固有の継続構文が必要な場合は対象シェルを明記し、表示幅だけを理由に実行できない改行を入れません。
- 置換が必要な値は原則として `<input-path>` などで表し、何に置き換えるかを説明します。
- `C:/path/to/input` などの例示用パスを使う場合も、実在するパスへの置換が必要だと分かるようにします。
- 例示する引数・設定キーは実在するものに限ります。本書のような汎用ガイドでは、説明用の例であることを明記します。

「コピーして使える」は、必要な準備と明示した値の置き換えを済ませれば実行できることを意味します。
プレースホルダーを含む例を、無編集で実行できると説明しません。

### 6.4. リンクには読む目的を添える

リンクは「こちら」だけでなく、参照先の内容や読む目的が分かる名前にします。
同じリポジトリ内では相対リンクを使い、個人環境の絶対パスへ依存させません。
ファイルの存在に加え、章内リンクの参照先、改名・章番号変更後のアンカーも確認します。
移植先が未確定の外部資料は、文書名や識別可能なファイル名で示し、存在しない相対リンクを作りません。

## 7. 正確さと説明の根拠

読みやすい文書であることと、仕様が正しいことは別々に確認します。
既存 README、改善案、サンプル設定、記憶のいずれも、単独で正しさの根拠にしません。

| 記述する事実 | 確認先の例 |
| --- | --- |
| 必要環境・依存関係・インストール方法 | パッケージ定義、配布設定、導入手順の確認結果 |
| コマンド・オプション・既定値 | CLI 定義、設定定義、現在の `--help`、関連テスト |
| 設定の形式・解決方法 | 設定スキーマ、読込処理、同梱設定、関連テスト |
| 出力の形式・保存先・変更条件 | 出力処理、仕様書、匿名の生成物、関連テスト |
| 対応環境・連携動作 | 対象環境の確認記録、実行結果 |
| 外部サービスの要件 | 対象サービスの公式資料と適用時点 |

仕様書は意図する契約、コードは実装、実行結果は確認した条件での動作を示します。
これらが食い違う場合は、都合のよい記述を選んで矛盾を隠しません。
記述できる現状と未解決の差を分け、必要な対応を作業結果に残します。利用・変更の判断に影響する差は、該当する現行文書にも明記します。
仕様が採用済みであること、実装済みであること、動作を検証済みであることを区別し、未採用の提案や未実装の仕様を現在の機能として説明しません。
主要な設計判断は、制約と採用理由を関連文書に残し、必要に応じて判断記録へリンクします。

未確認の事項は断定せず、利用判断に必要なら「未検証」と、確認できていない範囲を明記します。
コードを読んだだけで、実環境での動作を確認済みとは書きません。
テスト成功も、外部サービスの認証や生成 AI の出力品質まで保証する根拠にはしません。
検証結果には対象バージョンまたは commit、実施日、環境・条件、確認した動作、未検証事項と結果への参照を示します。作業中の変更がある場合はその範囲も示し、同じ commit の内容と混同しません。根拠のない版・日付・結果を補いません。
検証手順を記載しただけで実施済みとは扱わず、以前の成功記録を別の版や条件での検証結果として示しません。
価格、モデル名、サービス名、対応範囲など変わり得る事実は、必要に応じて一次資料と確認時点を示します。

## 8. 執筆・更新の手順

### 8.1. 対象と根拠を確認する

1. 個別依頼、適用される方針、`AGENTS.md`、対象文書、関連仕様を読みます。
2. 未コミットの変更や作成中の文書を確認し、既存の編集内容を把握します。
3. 想定読者、最初に達成する作業、今回変更する文書の範囲を決めます。
4. 記述・変更する事実を、実装・設定・テスト・出力例などに照合します。

文書の改訂依頼を理由に、実装、実データ、上位方針、他のリポジトリまで変更しません。
実装変更が必要な差は、文書修正と分けて報告します。

### 8.2. 情報を保持して再構成する

全面的な再構成では、元の説明を「現在の読者に必要か」で判断し、必要な情報の配置先を決めます。
情報の保持は、既存の全文を残すことを意味しません。現在の利用判断や操作に不要な説明は削除できます。

| 元の説明 | 扱い |
| --- | --- |
| 現在も必要な仕様・手順・制約 | 適切な章へ保持または移動します。 |
| 複数箇所にある同じ説明 | 意味と条件を保ち、詳細を1か所へ統合します。 |
| 既存利用者に必要な移行・互換性の情報 | 対象バージョンと必要な操作を、保守・移行の説明として残します。 |
| 現在の判断に不要な開発経緯・内輪の作業分担 | READMEから削除します。保守に必要な場合だけ、変更履歴や設計記録へ移します。 |
| 古い、誤っている、根拠を確認できない説明 | 訂正・削除・未確認の明示を選び、重要な変更の理由を作業結果に残します。 |

情報量が多い場合は、元の節・新しい配置先・扱いを対応させた表を作業用に用意すると、脱落を確認しやすくなります。
現在の利用に必要な上書き条件、再開条件、互換性、制約などを、短くすることだけを目的に消さないことを必須とします。
公開READMEでは、個人用リポジトリ名や非公開の依頼文・開発体制を前提にせず、利用者が用意するものと操作を説明します。
「過去のバージョン」という理由だけで削除せず、現在の利用者に必要な移行情報かを判断します。

### 8.3. 追記を適切な場所へ統合する

変更点は、読者がその情報を必要とする章に組み込みます。
新機能の説明を末尾や冒頭へ継ぎ足すだけで終わらせません。
共通仕様、設定例、図、コマンド一覧、関連リンクなど、その変更で古くなる説明を合わせて直します。
動作を変更する作業では、関係する README・詳細文書・CHANGELOG を同じ作業で更新します。各文書は現在の使い方・契約・設計理由を保ち、CHANGELOG は利用者への影響と必要な対応を記録します。
文書を移動するときは、README・文書間リンクに加え、生成処理や検証処理からの参照も更新します。
複数の言語版がある場合は、対応する情報の配置と参照先を確認します。
各文書に古いパスが残っていないかを確認します。

小さな修正では、関連する範囲の整合を取ります。
本書の標準構成に合わせるためだけに、無関係な章まで全面的に書き換える必要はありません。
「今回何を変更したか」は作業報告や変更履歴へ、README には「現在どう使うか」を書きます。

### 8.4. 読み手として確認する

1. 初見の利用者として、タイトルと冒頭から用途を理解でき、前半だけで準備から結果確認まで進めるかを追います。
2. 既存利用者として、設定変更・再実行・失敗時の対応を目的から探せるかを確認します。
3. 元の文書と比較し、有用な説明と条件が残っているかを確認します。
4. 各段落について、読者のどの判断・操作に必要かを確認し、不要な説明と重複を削ります。
5. 記述した事実、例、リンク、Markdown の構造を確認します。
6. 成果物を確認する人として、README から仕様・設計理由・検証根拠へ到達でき、現在の状態と未実装・未検証の範囲を判断できるかを確認します。

確認は、静的な照合や既存のテスト結果を優先し、必要な場合に関連箇所の限定した検証を行います。
実行する前に、そのコマンドが書き込み・通信・認証などを伴うかを確認します。
文書の確認のために、実データの変更や課金を伴う処理を無断で実行しません。

## 9. 主言語と補助言語

### 9.1. 対象ユーザーに合わせて言語を選ぶ

`README.md` をリポジトリの入口となる主文書とし、英語で作成することを基本とします。
主要な対象ユーザーが日本語話者であることが明確な場合は、`README.md` を日本語で作成できます。
補助言語版を用意するかは、対象ユーザーの必要性、公開・利用の範囲、継続して更新できるかを踏まえて判断します。

| 状況 | 主文書 | 任意の補助言語版 |
| --- | --- | --- |
| 基本の構成 | `README.md`：英語 | `README_ja.md`：日本語 |
| 主要な対象ユーザーが日本語話者であることが明確 | `README.md`：日本語 | `README_en.md`：英語 |

どちらの場合も、`README.md` だけで構いません。
日本語版や英語版の補助文書を、一律の必須成果物にしません。
新規作成で主言語の指定や日本語話者を主対象とする明確な条件がなければ、英語の `README.md` を作成します。
依頼文や参考資料が日本語であることだけを、対象ユーザーが日本語話者である根拠にしません。
既存文書の改訂では、現在の言語構成と依頼範囲を確認し、言語やファイル名の変更を目的に含まない場合は、その構成を保ちます。

### 9.2. 複数の言語版を維持する場合

主文書と補助言語版は、同じ事実と利用条件を伝える文書として管理します。
各文書の先頭付近に、実際に存在する言語版への相互リンクを置きます。

- コマンド、設定値、前提、手順、制約、注意、結果の解釈を意味的にそろえます。
- 各言語で自然に読める文章にします。逐語訳や、改行位置の一致は求めません。翻訳元を見なくても、目的・対象・動作・条件の関係が一読で分かるか確認します。
- 主要な章の対応と情報を見つけやすい構成を保ち、必要なら小見出しや段落順を調整します。
- 図の構成要素と関係、例の入出力、リンク先の役割も一致させます。
- 仕様変更では原則として維持している各言語版を同時に更新します。明示的に一部の言語版だけを対象とする依頼では、その範囲を守り、同期が必要な箇所を作業結果で示します。

公開時の入口となる言語と、執筆・翻訳の基準となる言語は区別します。
日本語版を編集上の正本とし、英語版を後続の翻訳工程で生成する運用も可能です。
その運用が指定されている場合は、依頼された翻訳元だけを編集し、生成先は翻訳工程で更新します。ファイル名は変更しません。
翻訳時には、確定した内容を基準に、事実に矛盾がないことと、重要な手順や条件が欠けていないことを確認します。

## 10. 完了前の確認

以下は、今回の変更範囲と関連する記述について確認します。
適用外・未確認の項目を、確認済みとして扱いません。

### 内容と構成

- [ ] タイトルと冒頭で用途・入力・得られるものを判断でき、成果物と実行報告を混同していない。
- [ ] 必要な用語が説明され、出力例や全体像が理解を助けている。
- [ ] 最初の利用手順がつながり、保存先と結果確認まで分かる。
- [ ] 日常利用、詳細、保守・移行、開発を目的から探せる。
- [ ] 詳細文書の役割と正本が明確で、README から読む目的が分かるリンクで到達できる。分類だけを目的とした空の文書・フォルダを作っていない。
- [ ] 現在の仕様・設計理由・手順が引き継ぎ文書だけに残らず、現行文書と時点を持つ記録を区別している。
- [ ] 必要な説明が適切な場所に残り、不要な説明、重複、内輪の開発経緯を削っている。

### 事実と操作

- [ ] コマンド、オプション、設定キー、既定値が確認した実装・仕様と一致している。
- [ ] CLI に `--help` と `--version` が実装され、単独で表示して正常終了することと、バージョン表示がパッケージ情報と一致することを確認した。README のインストール確認に `--version` の実行例と判断基準がある。
- [ ] 条件、単位、対象範囲、再実行時の影響が曖昧でない。
- [ ] 通信・外部送信・費用・上書きなど、実行前に必要な条件が分かる。
- [ ] 対応と未検証、実出力と説明例、見積もりと実測値が区別されている。
- [ ] 意図する契約、実装済みの動作、未実装の仕様・提案を区別し、不一致があれば現状と必要な対応を示している。
- [ ] 検証結果の対象版・実施日・条件・確認範囲・未検証事項を確認でき、過去の結果を現在の保証として扱っていない。
- [ ] 動作を変更した場合、関係する README・詳細文書・CHANGELOG の説明が整合している。
- [ ] 移行・互換性に必要な説明が残り、古い操作を現行の推奨手順として示していない。

### 表現と形式

- [ ] 一文と一段落の内容を追いやすく、日本語本文に不要な文中改行がない。
- [ ] 例の準備・置換値・作業フォルダが明確で、コマンドと設定の構文が正しい。
- [ ] 相対リンクと章内リンクの参照先が存在し、リンク名が内容に合っている。
- [ ] 手動の目次がなく、冒頭で初回に読む範囲と必要時に参照する範囲を案内している。
- [ ] 表の列とコードフェンスが整い、追加・変更した図の構文を確認した。
- [ ] 個人の実パス、認証情報、非公開データを例や本文へ持ち込んでいない。
- [ ] `README.md` の言語と補助言語版の有無が、対象ユーザーと依頼範囲に合っている。
- [ ] 複数の言語版がある場合、相互リンクと更新対象が適切である。同時更新なら内容の整合を確認し、別工程で翻訳する運用なら翻訳元と後続工程を作業結果に示している。

図や複雑な表を変更した場合は、可能な範囲で実際の表示も確認します。
表示未確認や動作未検証が残る場合は、その範囲を作業結果に記載します。
必須の情報不足や記述の矛盾は修正し、確認できない事項は断定を避けたうえで残る課題を報告します。

## 11. 生成 AI への依頼テンプレート

本書と必要に応じて基本方針を渡し、次の形で依頼できます。
山括弧の項目を対象に合わせて置き換えます。

```text
添付した「CLIリポジトリREADME執筆規約」に従い、次の README を新規作成または改訂してください。

対象文書：<変更するファイル>
想定読者：<主要な対象ユーザー、その言語と前提知識>
最初に達成する作業：<読者が行えるようにしたいこと>
参考資料：<仕様、実装、出力例、参考にする文書>
変更範囲：<今回変更してよい範囲>
主言語：<README.md の言語。新規作成では英語が基本。日本語にする場合は対象ユーザーも明記>
補助言語版：<不要、README_ja.md、README_en.md など。新規作成か既存版の更新かも明記>
翻訳運用：<執筆上の正本と翻訳先。同時更新か、正本だけを編集して別工程で翻訳するか>

着手前に、適用される方針と未コミットの変更を確認してください。
参考文書の構成や表現から原則を抽出し、固有の機能や数値は転用しないでください。
記述する事実を確認し、初回利用と必要時の参照を両立する構成にしてください。
読者の判断・操作に必要な情報と安全条件を保持し、不要な説明・重複・古い記述・関連リンクを整理してください。
依頼範囲外の実装や実データは変更しないでください。
完了時に、主な編集判断、確認結果、未確認事項、残る課題を報告してください。
```

## 12. 参考実例と使い方

参考実例は、読者の目的と対象CLIに合うものを選び、参照版と閲覧方法を確認します。
本書の作者による実例として、[Tkn Excel Note の README](https://github.com/tuckn/tkn_excel_note/blob/6564da7d86a251a8a2b5ed4fc16c43a5d500e422/README.md) を挙げます。
参照版は Git リビジョン `6564da7d86a251a8a2b5ed4fc16c43a5d500e422` に固定しています。
参考実例から取り入れる観点は次のとおりです。

- 冒頭で初回利用と詳細参照の読み方を案内する。
- 用途を説明した直後に、得られる成果を小さな実例で伝える。
- 対象範囲、用語、全体像を用意し、操作前の理解を助ける。
- セットアップ、初回実行、日常の更新、結果確認をつなげる。
- 設定と影響、状態と対応、保存領域と失った場合の影響を表で示す。
- 詳細な設定・保存構造・制限・保守・開発を後半から参照できるようにする。

固有のコマンド、保存領域の数、モデル、スキーマの版、上限値は対象 CLI に合わせます。
実例の記述を、他のリポジトリの機能の根拠にはしません。
規則は本書、対象 CLI の事実はその仕様と実装で確認します。
